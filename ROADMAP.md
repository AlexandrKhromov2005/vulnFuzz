# vulnFuzz: архитектура и план blackbox MVP

Проект курсовой работы «Метод и инструмент выявления недекларированных возможностей в бинарном ПО на основе фаззинга с обратной связью по покрытию и анализа непокрытого кода».

Актуализировано: **10 ноября 2026**. Эта редакция заменяет прежний план одиночного ELF/stdin-фаззера. Целевая система — исследовательский blackbox-инструмент полносистемного фаззинга VM-сценариев с concolic DSE. Точные модели данных находятся в [docs/CONTRACTS.md](docs/CONTRACTS.md), задачи и критерии приёмки — в [docs/BACKLOG.md](docs/BACKLOG.md).

## 1. Цель и допустимые выводы

На вход исследователь передаёт:

- неизменяемый образ изолированной Linux x86-64 VM;
- идентификатор начального snapshot;
- путь к исследуемому ELF внутри guest;
- бюджеты кампании и конфигурацию детерминированной VM.

Исследуемый бинарь может быть stripped, PIE/non-PIE, без секций, символов, исходников и debug info. Символы и найденный `main` являются только необязательными подсказками.

Инструмент автоматически исследует интерфейсы цели, строит и мутирует сценарии действий, собирает покрытие и эффекты, применяет concolic DSE и формирует отчёт о **кандидатах на потенциально недекларированное поведение**.

Без внешней спецификации инструмент не может доказать, что поведение действительно не задумано разработчиком. Поэтому различаются:

- наблюдаемый факт — блок, эффект или исход зафиксированы конкретным запуском;
- аномалия — поведение выделяется относительно других сценариев;
- воспроизводимая аномалия — результат повторяется из идентичного состояния;
- контролируемый триггер — минимальное изменение сценария включает и выключает поведение;
- DSE-validated trigger — solver нашёл условие, а конкретный QEMU-запуск подтвердил его.

Сильное заключение формулируется как «обнаружена воспроизводимая потенциально недекларированная возможность» с указанием сценария, эффекта и доказательств. Оно не означает автоматический вердикт о вредоносности.

## 2. Текущее состояние кода

База аудита — `main`, коммит `39bf206`. Реализован только статический прототип:

- `src/loader.rs`: ELF64 little-endian x86-64, ET_EXEC и динамический PIE ET_DYN, загрузка файловых частей `PF_X PT_LOAD`, проверки диапазонов/overflow/alignment/overlap, `read_va`, необязательная подсказка `main`;
- `src/disasm.rs`: линейное декодирование Capstone, прямые цели, виды потока, операнды и явный неразобранный суффикс;
- `src/main.rs`: inspection CLI для одного ELF;
- `src/model.rs` и `tests/contracts.rs`: строгая Rust-модель Contracts v2, канонические идентификаторы, ContextPatch и 9 интеграционных тестов;
- `src/lib.rs` и `tests/elf.rs`: библиотечная цель, 14 интеграционных тестов и doctest, включая PIE/non-PIE и sectionless ELF.

Проверки на момент аудита: `cargo test --locked` проходит; `cargo fmt --all -- --check` и строгий Clippy не проходят. QEMU в среде не установлен.

Отсутствуют runner, QEMU backend, динамический CFG, VM orchestration, покрытие, фаззер, DSE, кампания, replay и отчёты. Текущий loader/disasm переиспользуются как вспомогательные компоненты, но не определяют границы новой архитектуры.

## 3. Рамки MVP

| Решение | Обязательный объём MVP |
| --- | --- |
| Guest | Linux x86-64, один заранее выбранный ELF внутри VM |
| Backends | Основной `qemu-system`; дополнительный быстрый `qemu-user` для ELF и тестов |
| QEMU | Собственный pinned fork + TCG plugins; SHA и патчи фиксируются |
| VM | Детерминированный аппаратный профиль, виртуальные часы, контролируемые RNG и внешние события |
| Состояние | Цепочки snapshot/action; разветвление от промежуточных состояний |
| Управление | Guest agent через изолированный канал; модифицировать исследуемый ELF не требуется |
| Discovery | Автоматические probes CLI, файлов, env, cwd, stdin и времени |
| Фаззинг | Мутации всего сценария и доступного контекста, не только stdin |
| DSE | Concolic execution исследуемого процесса, Z3 bitvectors; конкретная проверка каждого решения |
| Oracle | Аномалии без спецификации, минимальные пары и уровни доказательности |
| Безопасность | Одноразовые VM, read-only исходные образы, нет host-сети/shared folders, обязательные лимиты |
| Демонстрация | Контрольные VM-фикстуры и один реальный stripped CLI без встроенного ответа |

В MVP сеть и IPC могут обнаруживаться и записываться как `unsupported_source`, но их автоматическая мутация не обязательна. GUI, Windows, ARM64, автономный выбор произвольных бинарников в VM и production-масштабирование не входят.

После MVP планируются сетевые/device inputs, stateful services, больше процессов, DSE библиотек и затем ядра VM. Модель `SourceId` и границы backend должны допускать это расширение без смены формата кампании.

## 4. Сквозной цикл

```text
VM image + snapshot + target path
  → проверка изоляции и идентичности образа
  → Discovery Engine: безопасные probes интерфейсов
  → начальные TestCase и Action[]
  → конкретное исполнение цепочки под QEMU
  → покрытие + mappings + эффекты + промежуточные snapshots
  → развитие динамического CFG
  → выбор цели: новый путь, аномалия или сложное условие
  → обычные мутации контекста и/или concolic DSE
  → ContextPatch и новый TestCase
  → конкретная проверка и пополнение corpus/state graph
  → минимизация и независимые повторы
  → findings + report.json + report.md + replay
```

DSE не запускает собственный обходной исполнитель: каждый кандидат проходит общий campaign runner, бюджет, журнал и конкретную валидацию.

## 5. Архитектура компонентов

| Модуль | Ответственность |
| --- | --- |
| `model`, `store` | Versioned TestCase, идентификаторы, события, snapshots, findings, атомарное хранение |
| `backend/qemu_system` | VM lifecycle, devices, clock, snapshot/restore, system plugins, guest address spaces |
| `backend/qemu_user` | Быстрый запуск Linux ELF и адресное покрытие с общей моделью наблюдений |
| `guest_agent` | Spawn, argv/env/cwd, stdin/files, PID/mappings, stdout/stderr и guest-эффекты |
| `discovery` | Ограниченные probes и создание начальных действий по наблюдаемым интерфейсам |
| `scenario` | Декларативные действия, мутации, минимизация и ContextPatch |
| `state_graph` | StateNode, snapshot lineage, разветвления и сравнение префиксов |
| `coverage`, `mapping` | PC → mapping → ELF VA; качество снимков; observations конкретного step |
| `dynamic_cfg` | Достраивание блоков/рёбер по трассам, AnalysisRevision и unknown-области |
| `corpus`, `campaign` | Очередь, novelty, бюджеты, RNG, обычные и DSE-фазы |
| `trace`, `symbolic`, `solver` | Выборочная трасса, taint, path constraints, Z3 и ContextPatch |
| `effects`, `analysis` | Поведенческие события, минимальные пары, аномалии и ранжирование |
| `replay`, `report` | Воспроизведение префиксов, подтверждения и доказательный отчёт |

Общие структуры не должны зависеть от физического транспорта backend. mmap пригоден qemu-user; system-mode может использовать отдельный shared-memory/virtio канал, но оба выдают один `CoverageSnapshot`.

## 6. Детерминированная VM и цепочки состояний

### 6.1. Детерминированный профиль

Fork QEMU и конфигурация VM должны обеспечивать:

- фиксированные машину, CPU, RAM и разрешённый набор устройств;
- виртуальные часы и явный `advance_clock` между действиями;
- контролируемые источники случайности;
- отсутствие неучтённых host network, RTC, entropy и shared filesystem;
- snapshots RAM + device state + copy-on-write disks, а не только диск;
- воспроизводимый порядок команд agent и внешних событий;
- обнаружение неподдерживаемого устройства/события с отказом, а не молчаливым best effort.

QEMU record/replay может использоваться там, где выбранный профиль его поддерживает, но не считается доказанным до эксперимента. Для подтверждений обязательны повторы из исходного snapshot и сравнение покрытия/эффектов.

### 6.2. Сценарий и граф

`TestCase` содержит начальный snapshot, VM config, target ref и упорядоченный `Action[]`:

```text
S0 --spawn------> S1 --stdin------> S2 --advance_clock--> S3
 |                 |
 |                 └--write_file--> S4
 └--other_case-------------------> S5
```

Поддерживаемые действия MVP: `spawn_process`, `write_stdin`, `write_file`, `set_env`, `advance_clock`, `checkpoint`. Аргументы/env могут быть частью `spawn_process`; отдельный `set_env` применяется только к последующим spawn и не меняет host env.

Фаззер может изменять параметры, вставлять/удалять/переставлять действия, менять часы и ответвляться от checkpoint. Каждый checkpoint сохраняет snapshot, родителя, action index, AnalysisRevision и digest наблюденных эффектов. Полный digest RAM не является единственным семантическим доказательством эквивалентности состояний.

Finding ссылается на префикс сценария и action index. Replay обязан восстановить весь префикс, а не только последний вход. Ускоренный replay от ближайшего snapshot периодически проверяется против полного replay от начального.

## 7. Автоматический Discovery Engine

Discovery исследует интерфейсы известной цели, а не выбирает любую программу в ОС. Начальные probes выполняются в одноразовых снимках:

- запуск без аргументов, с `--help` и `--version`;
- пустой, короткий и повреждённый stdin;
- вариации cwd и ограниченного базового env;
- несколько значений виртуальных часов;
- контролируемые файлы в рабочем каталоге.

По наблюдениям QEMU и agent создаются `InterfaceHint`: чтение stdin, открытие файлов, env-зависимость, обращения к часам, попытки network/IPC, spawn и эффекты. Подсказка не считается доказанным интерфейсом, пока не проверена отдельным сценарием.

Результат discovery — начальные TestCase и явный список unsupported/unknown. Неограниченный перебор всех путей, деструктивные probes и автономное взаимодействие с GUI в MVP запрещены.

## 8. Динамическая модель кода и адресов

Динамический анализ основной, статический — вспомогательный:

1. Loader извлекает executable ranges из PT_LOAD, если секции отсутствуют.
2. Статический анализ начинается с entry и доступных прямых рёбер, но не обязан найти `main`.
3. Реальные PC подтверждают инструкции и достраивают блоки/рёбра.
4. Конфликтующие и непроверенные байты остаются `UnknownRegion`; линейный разбор не выдаёт данные за код.

Стабильный `BlockId = (BinaryId, start_elf_va)`. Runtime-наблюдение дополнительно содержит `MappingId`: BinaryId, load bias, address-space identity и mapping generation. PID без поколения не является идентичностью, поскольку PID и VA могут использоваться повторно.

Для system-mode учитываются CR3/ASID или эквивалентный механизм backend, process mappings, ASLR, загрузка и выгрузка. Библиотеки и ядро помечаются `out_of_scope`, пока не выбраны для анализа.

CFG растёт между итерациями. Каждая версия имеет `AnalysisRevision`; BlockId остаётся стабильным при добавлении новых знаний. Покрытие разных BinaryId не объединяется, а сравнение процентов между AnalysisRevision выполняется только с явным общим знаменателем и пересопоставлением.

Состояния блоков: `covered`, `not_observed`, `unknown`, `out_of_scope`. Partial coverage даёт только положительные факты; invalid не участвует в novelty. Посещение двух блоков не доказывает прохождение ребра.

## 9. Concolic DSE с Z3

MVP символически анализирует только исследуемый процесс. Ядро, QEMU, устройства и библиотеки выполняются конкретно; библиотечные вызовы либо моделируются отдельно позже, либо обрывают symbolic path с причиной.

Для выбранного step и ветвления:

1. QEMU включает выборочную инструкционную/памятную трассу, а не постоянную запись всей VM.
2. Taint sources связываются с полями действий через `SourceId = (action_index, field, offset, length)`.
3. Строятся bitvector path constraints до выбранного `jcc`; независимые от входа условия не решаются как символические.
4. При инверсии ветви solver возвращает модель либо `unsat`, `unknown`, `timeout`, `unsupported`.
5. Модель преобразуется в `ContextPatch`, сохраняя ширину, endian и ограничения поля.
6. Новый TestCase конкретно исполняется под QEMU. Достижение цели засчитывается только по наблюдению.

Solver не изменяет VM напрямую и не считается доказательством достижимости. `unsat` относится только к построенной модели и её допущениям. Ограничиваются длина трассы, число инструкций/ограничений, память и время solver.

В будущем `SourceId` расширяется на сеть/устройства, а symbolic scope — на библиотеки и ядро без изменения уже сохранённых идентификаторов.

## 10. Фаззинг контекста и кампания

Единица corpus — TestCase с хешом канонического содержимого. Мутации включают:

- bytes/stdin/files: flip, insert/delete/replace, arithmetic, splice;
- argv/env: замена, добавление и удаление значений из допустимого пространства;
- cwd и имена файлов внутри разрешённого guest workspace;
- виртуальное время и интервалы между действиями;
- вставку, удаление, дублирование и перестановку действий;
- выбор другого родительского snapshot и префикса;
- ContextPatch от DSE.

Ограничения длины, числа действий, размера файлов, VM RAM, virtual/wall time и solver budget входят в manifest. RNG seed и канонический порядок corpus сохраняются.

Бюджеты раздельно учитывают VM episodes, запуски цели, wall time, virtual time и solver calls. Ошибка до создания VM/процесса не выдаётся за исполнение цели, но журналируется. Crash/timeout сохраняются независимо от нового покрытия.

Приоритет имеют новые validated-блоки, редкие условия, уменьшение статической дистанции и новые эффекты. Это эвристики исследования, а не оценка вредоносности.

## 11. Аномалии, доказательства и отчёт

Источники сигналов:

- редкий путь, достижимый только при особом сочетании условий;
- сложный предикат, пройденный DSE;
- малое изменение контекста с большим расхождением трассы/эффектов;
- новые файловые, процессные, сетевые или временные эффекты;
- отсутствие соответствующего ожидаемого действия в сценарии;
- различие поведения при почти одинаковом наблюдаемом выводе.

Уровни `Finding`: `static_hypothesis`, `observed_anomaly`, `reproducible_anomaly`, `controlled_trigger`, `dse_validated_trigger`. Для повышения уровня нужны независимые повторы; для controlled trigger — минимальная пара включения/выключения; для DSE level — solver model и конкретное подтверждение.

`anomaly_score` используется для сортировки и сопровождается объяснимыми факторами. Он не превращается в вероятность вредоносности. Итоговый отчёт содержит:

- идентичность VM, QEMU, agent, solver, ELF и конфигурации;
- TestCase, ContextPatch и префикс состояния;
- блоки, условие, эффекты, stdout/stderr и исходы;
- минимальную пару и число повторов;
- качество покрытия, unknown, unsupported и ограничения DSE;
- отдельные факты, эвристики и заключение исследователя.

Обязательны отрицательные фикстуры с обычными редкими ветками, `--help`, env и временными проверками. Они не должны получать сильное заключение только из-за редкости.

## 12. Изоляция и жизненный цикл

Запуск разрешён только в одноразовой изолированной VM:

- исходный образ read-only, изменения на CoW-слое;
- нет host-сети, общих каталогов, host devices и неявных credentials;
- канал agent не доступен исследуемому процессу как host-control interface;
- обязательные wall/virtual timeout, RAM/CPU/disk/output limits;
- по timeout/cancel/QEMU failure выполняются остановка, reaping и очистка snapshot/processes;
- сбой backend не классифицируется как падение цели;
- артефакты потенциально опасны и открываются только как данные.

Это ограничение эксперимента, а не заявление о полноценной malware sandbox. Для реальных вредоносных образов требуется отдельная внешняя изоляция учебной среды.

## 14. Эксперимент и готовность MVP

Контрольные VM-фикстуры:

- `branches`: известные блоки и два пути;
- `trigger`: несколько простых и составных сравнений, DSE-trigger;
- `time_bomb`: поведение зависит от виртуальных часов;
- `env_file`: триггер требует сочетания env, файла и stdin;
- `stateful`: триггер проявляется только после цепочки действий;
- `benign_uncovered`: обычные редкие ветки без особого эффекта;
- `crash_hang`: падение и зависание;
- `mapping`: PIE/ASLR, exec, unload и повторное использование адресов;
- `real_cli`: реальный stripped бинарь без встроенного ответа.

Независимые оракулы создаются из исходников/меток до strip и не передаются инструменту. Для VM сохраняются hashes образа, snapshot, firmware, QEMU и agent.

MVP готов, когда:

1. Чистая среда собирает Rust, pinned QEMU, plugins, agent и solver; CI проверяет unit/integration tests.
2. Один и тот же TestCase повторно даёт одинаковые нормализованные наблюдения в заявленном детерминированном профиле; несовпадения явно ограничивают вывод.
3. System-mode корректно сопоставляет coverage при ASLR и повторных mappings; qemu-user даёт совместимый результат на общей ELF-фикстуре.
4. Discovery без исходников цели создаёт начальные CLI/file/env/time сценарии, а unsupported источники видны в отчёте.
5. Мутации цепочки достигают `stateful`, включая требуемую последовательность действий и часов.
6. DSE самостоятельно находит вход для контрольного составного условия, а конкретный запуск подтверждает целевой BlockId. Триггер не зашит в инструмент.
7. Для controlled trigger минимальная пара и полный replay воспроизводят эффект; сбой QEMU не выдаётся за поведение цели.
8. Отрицательные фикстуры не получают сильное заключение только по редкости; отчёт содержит unknown/unsupported и не завышает покрытие.
9. Выполнен эксперимент на контрольном образе и одном реальном CLI. Положительный прирост DSE над обычным фаззингом желателен, но отрицательный результат тоже публикуется.
10. Нет открытых P0/P1, все команды README и replay выполнены вторым участником на чистой VM.

### Протокол сравнения

Сравниваются обычный context fuzzing и тот же fuzzing + DSE на одинаковых начальных сценариях, snapshots, RNG seeds, аппаратном профиле и бюджетах. Метрики: покрытые validated-блоки с общим знаменателем, время/запуски до триггера, число успешных серий, solver calls/success/timeout, VM episodes/s, wall time, replay failures и false-positive разбор.

Неуспешные попытки и ограничения сохраняются. Десяти повторов достаточно для учебной оценки, но не для универсальных статистических выводов.

## 15. Основные риски

| Риск | Ранняя проверка | Действие |
| --- | --- | --- |
| VM не воспроизводится | Два replay одного episode до fuzzing | Сузить devices/события, исправить fork; best effort не выдавать за детерминизм |
| System mappings неверны | ASLR/unload/exec фикстуры | Остановить кампанию при неоднозначном MappingId |
| Постоянная трасса слишком дорога | Замер overhead на branches | Выборочная трасса только вокруг цели/DSE |
| Цепочки действий взрывают пространство | stateful с малым грамматическим бюджетом | Ограничить действия, использовать checkpoints и минимизацию |
| DSE тонет в ограничениях | Составной trigger с лимитами | Сузить окно/scope, сохранить unsupported/unknown |
| Аномалии дают ложные выводы | Отрицательные фикстуры и ручной разбор | Понизить уровень, требовать минимальную пару и replay |
| Оба backend удваивают работу | Общий контракт наблюдений на одной фикстуре | Общие analysis/report; низкоуровневые transport остаются раздельными |
| Объём MVP чрезмерен | Сквозные этапы I1/I3 как ранние рубежи | Сокращать интерфейсы/набор фикстур по решению владельца, не скрывая непроверенные части |
