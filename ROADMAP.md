# Завершение vulnFuzz до MVP

Практический план курсового проекта «Метод и инструмент выявления недекларированных возможностей в бинарном ПО на основе фаззинга с обратной связью по покрытию и анализа непокрытого кода».

Дата аудита: **26 октября 2026**. База плана: ветка **`main`**, коммит **`1447963d4912362766ebf0587ef9f280fd5365c4`** (`remove magic numbers`). Прочитаны все семь отслеживаемых файлов. `AGENTS.md`, README, предыдущие планы и тесты отсутствуют.

Раздел аудита описывает существующий код; остальные разделы — план разработки. Подробные задачи находятся в [docs/BACKLOG.md](docs/BACKLOG.md).

Дополнительные выводы аудита:

- `vF_get_section_bytes` возвращает копию только при точном совпадении адреса с началом секции. Это не функция чтения произвольного VA.
- В `lea` адрес вычисляется как `address + size + (disp as u64)`. Отрицательное смещение способно вызвать панику в debug или оборачивание в release, в том числе на обычной RIP-relative ссылке назад. Этот случай требует отдельного теста.
- В `goblin 0.10.7` `Elf::parse_with_opts` проверяет некоторые таблицы через `SectionHeader::check_size_with_opts`, но не вызывает её для каждой исполняемой секции. Поэтому проекту нужны собственные проверки используемых диапазонов.
- `disasm_all` может вернуть разобранный префикс; код не сверяет суммарные размеры с длиной входа. `syscall`, `ud2`, `hlt`, непрямые jump/call и необычные терминаторы требуют явной политики. `main` не должен быть обязательной точкой старта анализа.
- `src/mod.rs` содержит `pub mod loader; pub mod disasm;`, но Cargo собирает бинарный crate из `src/main.rs` с собственными `mod`. Отдельной библиотечной цели сейчас нет.

## 2. MVP

### Поддерживаемый профиль

Обязательный профиль: Linux x86-64; обычные ELF64 little-endian ET_EXEC и исполняемые PIE ET_DYN; консольный, однопоточный процесс; один конечный вход через файл или stdin; размер входа до 4096 байт по умолчанию. Основной корпус проверок — программы GCC/glibc с обычными файловыми PT_LOAD, без упаковки и изменения исполняемого кода. Символы, исходники, найденный `main` и debug info не обязательны. Обязательны PIE/non-PIE, stripped и небольшой валидный пример без таблицы секций.

Этот профиль предстоит проверить на тестовой матрице. Необычные или перекрывающиеся сегменты, ET_DYN-библиотеки вместо запускаемой программы и некорректные файлы получают отказ с причиной. При неполной статической модели анализ может продолжиться, но неизвестные области должны попасть в отчёт.

### Сквозной сценарий и артефакты

**Проектируемые команды**, сейчас их нет. Пользователь передаёт бинарник `./sample` и каталог начальных входов `./seeds`. QEMU и клиент покрытия заранее установлены по инструкции сборки.

```sh
cargo run --locked --bin vulnFuzz -- run \
  --binary ./sample --input file --seeds ./seeds --out ./runs/demo \
  --mode guided --max-execs 10000 --timeout-ms 200 --max-input-bytes 4096 \
  --rng-seed 42 -- @@
```

`@@` — ровно один аргумент-путь к создаваемому файлу входа, без shell-подстановки. Для stdin: заменить `--input file` на `--input stdin`, убрать `@@`; после `--` остаются только аргументы цели. Каждый вход подаётся отдельным запуском процесса; persistent mode/forkserver не нужны. `--mode baseline` включает только обычные мутации с той же обратной связью по покрытию.

Порядок работы:

1. Проверить профиль ELF и SHA-256, построить частичный CFG.
2. Исполнить начальные входы, собрать покрытие и сопоставить его с CFG.
3. Запустить обычные мутации корпуса. Через каждые 100 запусков выбирать непокрытую цель и проверять до 100 направленных кандидатов.
4. Возвращать полезные входы в корпус и повторять цикл до исчерпания бюджета.
5. Повторно проверить находки и записать отчёт.

Все исполнения цели, включая начальные входы и подтверждения с QEMU и без него, входят в `max-execs` и раздельные счётчики. Для подтверждения резервируются шесть запусков: три с QEMU и три обычных. При нехватке бюджета находка остаётся неподтверждённой. Ошибка до создания процесса учитывается только во времени и счётчике ошибок; после трёх `SpawnError` подряд кампания прекращается.

```text
runs/demo/
  manifest.json          # схема, бинарник, версии, argv, env, cwd, бюджет, seed
  binary/target          # неизменяемая копия анализируемого ELF
  static.json            # сегменты, инструкции, блоки, рёбра, неизвестные области
  events.jsonl           # RunResult, происхождение входов, решения о целях
  runs/<run-id>/         # адресное покрытие, метаданные, ограниченные stdout/stderr
  corpus/<sha256>        # сохранённые входы; исходные seeds также сохраняются
  findings/<id>.json     # уровень доказательности и ссылки на вход/повторные запуски
  report.json
  report.md
```

При существующем `manifest.json` в `--out` отказывать в запуске. Каждый вход сохранять по хешу до передачи цели; журнал связывает его с RunId. Все JSON содержат `schema_version`; адреса записываются шестнадцатеричными строками, чтобы сторонние программы не теряли точность u64. Ротация результатов больших кампаний — после MVP.

```sh
cargo run --locked --bin vulnFuzz -- replay \
  --campaign ./runs/demo --finding finding-0001
```

Replay сверяет хеш ELF и версию исполнителя, повторяет сохранённый вход с прежней конфигурацией и сравнивает исход, покрытие выбранного блока и stdout/stderr. Исходники цели не требуются. Replay по `--run <run-id>` появляется уже в первом сквозном сценарии.

### Проверяемое определение готовности

MVP готов, когда на чистой заявленной Linux-среде выполнены все пункты:

1. Сборка с lockfile, модульные и интеграционные тесты проходят. Отдельная обязательная проверка CI запускает тесты с QEMU; его отсутствие считается ошибкой.
2. Одна команда `run` проходит весь цикл на наборах file/stdin, PIE/non-PIE/stripped; отсутствие `main` не останавливает кампанию. На контрольном sectionless ELF исполняемые диапазоны извлекаются из PT_LOAD.
3. Покрытие двух заранее известных путей совпадает с независимым адресным оракулом фикстуры; для PIE нормализация выдерживает повторные старты и проверку разных bias. Блоки вне восстановленной области не объявляются непокрытыми.
4. `baseline` сохраняет новые входы при новом блоке; `guided` после анализа фронтира генерирует вход, достигающий контрольного простого триггера. Есть события выбора цели, попыток и реально наблюдённого достижения. Триггер не зашит в код инструмента.
5. Для контрольного триггера и падения сохранённый вход даёт одинаковый результат в трёх запусках с QEMU и трёх обычных запусках. Для остальных целей несовпадение указывается в отчёте и ограничивает вывод средой QEMU. Зависание подтверждается только как превышение заданного лимита времени.
6. Таймаут, Ctrl-C, падение и неподдерживаемые дочерние процессы не оставляют запущенных целей; причина завершения записана в manifest. Ошибка исполнителя не записывается как падение цели.
7. Итоговый отчёт разделяет факты, эвристики, гипотезы и подтверждённое поведение; отрицательная фикстура с обычной редко используемой веткой не получает заключение «недекларированная возможность».
8. Сравнение baseline/guided выполнено по сохранённому протоколу, включая неуспешные попытки. Данные позволяют повторить измерения независимо от того, получен ли прирост покрытия.

### Объём

| Обязательно для MVP | Полезно после MVP | Вне текущего объёма |
| --- | --- | --- |
| Модель ELF/PT_LOAD и адресов; частичный CFG; один исполнитель; точное покрытие входов в блоки; корпус и мутации; выбор непокрытой цели; направленные кандидаты из констант; бюджет; replay; отчёт; фикстуры и эксперимент | Ускорение сбора покрытия, forkserver, минимизация входов, возобновление кампании, разбор таблиц переходов, сравнения строк и библиотечных функций, HTML/DOT, проверка на реальных CLI | ML, Z3, полноценное символическое исполнение, MCP, LLM-агенты, другие ОС/архитектуры, обязательная инструментализация исходников цели, GUI/сеть/ядро, анализ библиотек как отдельных целей, система плагинов |

## 3. Архитектура

### Модули и ответственность

Один Rust crate с библиотекой `src/lib.rs` и CLI в `src/main.rs`. Имеющиеся loader/disasm используются после исправлений. Для API QEMU нужен небольшой C-клиент.

| Модуль (предлагается) | Ответственность | Основные вход → выход |
| --- | --- | --- |
| `model.rs` | Общие ID, адреса, состояния, форматы схемы | Версионированные структуры без запуска процессов |
| `loader.rs` | ELF-профиль, хеш, PT_LOAD, преобразование VA/смещений с проверками, необязательные символы | файл → `CodeImage` или `LoadError` |
| `disasm.rs`, `cfg.rs` | Декодирование, лидеры, прямые рёбра и явные неизвестные переходы | `CodeImage` → `StaticModel` |
| `runner.rs` | Один запуск, argv/file/stdin, таймаут, лимиты, завершение процессов | `RunSpec`, `InputRef` → `RunResult` |
| `instrumentation/qemu/coverage.c`, `coverage.rs` | Сбор адресов, контроль протокола, нормализация, сопоставление | ELF/CFG, адресные события → `CoverageSnapshot` |
| `corpus.rs`, `fuzz.rs` | Хранение входов, RNG, очередь, обычные мутации, учёт запусков | корпус/бюджет → кандидаты/новое покрытие |
| `analysis.rs` | Непокрытые блоки, фронтир, расстояния, объяснимый порядок целей | CFG + покрытие → `Target` |
| `directed.rs` | Ограниченные кандидаты из констант и проверка достигнутой цели | `Target` + seed + лимит → `AttemptResult` |
| `campaign.rs` | Переход между baseline/guided-фазами, остановка | `CampaignConfig` → события/итог |
| `cli.rs`, `store.rs`, `report.rs` | Разбор аргументов, атомарные записи, replay, отчёт | конфигурация/события → артефакты |

### Исполнение и покрытие: выбор одного пути

| Подход | Применимость | Ограничение/стоимость | Решение |
| --- | --- | --- | --- |
| QEMU Linux user-mode + свой TCG-клиент | Без исходников; адреса guest-инструкций; можно проверять входы отдельных блоков | Внешняя сборка, API зависит от версии, эмуляция меняет среду и скорость | **Основной кандидат для MVP**, принимается по [VF-03](docs/BACKLOG.md#vf-03) |
| DynamoRIO + drcov/малый клиент | Динамическая инструментализация без перекомпиляции; выполненные блоки привязаны к модулям | Границы блоков могут отличаться от статических; сохранение результатов при SIGKILL требует проверки | Резерв при отрицательном VF-03 |
| `ptrace` + пошаговое исполнение/точки останова | Linux, доступ к RIP и регистрам; пригоден для независимой проверки маленькой фикстуры | Пошаговое исполнение медленно; обработка сигналов и точек останова требует собственной логики | Использовать только для диагностики |
| AFL++ QEMU bitmap как единственный источник | Готовая обратная связь для мутаций | Хешированная bitmap без адресного канала не даёт точного множества непокрытых блоков CFG | Не использовать для сопоставления CFG; подключение готового фаззера не требуется |

QEMU предоставляет callback выполнения инструкции и её виртуальный адрес ([руководство TCG Plugins](https://www.qemu.org/docs/master/devel/tcg-plugins.html)). У drcov есть журнал выполненных блоков на процесс ([документация DynamoRIO](https://dynamorio.org/page_drcov.html)). Сопоставление с нашим CFG и затраты исполнения предстоит измерить в VF-03.

Начальная версия для VF-03 — **QEMU v10.1.0**. Эксперимент фиксирует SHA, ABI, среду и команды сборки. Клиент ставит callback выполнения на первую инструкцию каждого проверенного CFG-блока, в том числе внутри блока трансляции QEMU (TB). Callback выставляет отдельный бит блока в общей mmap-области; сама трансляция бит не выставляет. Покрытие означает **наблюдение входа перед выполнением первой инструкции блока**. Оно сохраняется и при сбое на этой инструкции, но не доказывает завершение блока.

Клиент также собирает неизвестные PC внутри исполняемых PT_LOAD. На начальных входах включается трасса с лимитом 65 536 уникальных PC для проверки границ предполагаемых блоков. Переполнение отмечается в снимке; отсутствующие данные не подтверждают границы. Системные библиотеки исключаются из обоих каналов.

### Адреса, PIE и ASLR

Единая статическая координата — **ELF VA**, не смещение файла и не абсолютный runtime-адрес. Блок идентифицируется `(BinaryId, start_elf_va)`. `FileOffset`, `ElfVa`, `GuestVa`, `LoadBias` — разные типы-обёртки, адресные диапазоны полуоткрытые `[start, end)`.

- Для файловой части PT_LOAD: `file_offset = p_offset + (elf_va - p_vaddr)`, только если `0 <= delta < p_filesz`; каждую операцию проверять на переполнение. У области `p_memsz - p_filesz` нет байтов в файле.
- В QEMU: `guest_va = elf_va + load_bias`; обратно `elf_va = guest_va - load_bias`. Для non-PIE ожидается bias=0; для PIE он вычисляется на каждом запуске. Отключение ASLR не заменяет нормализацию.
- Основная привязка QEMU: `bias = qemu_plugin_start_code() - min(p_vaddr)` по исполняемым PT_LOAD главного ELF; сверить `qemu_plugin_end_code()` с `max(p_vaddr + p_filesz) + bias`. При инициализации vCPU проверить путь, хеш и контрольные байты главного ELF. В v10.1.0 границы вычисляются из PF_X-сегментов ([elfload.c](https://github.com/qemu/qemu/blob/v10.1.0/linux-user/elfload.c)); API объявлен в [qemu-plugin.h](https://github.com/qemu/qemu/blob/v10.1.0/include/qemu/qemu-plugin.h). Привязку динамического PIE проверить в VF-03.
- Нельзя вычислять bias по первому реально выполненному PC: первым может исполняться ELF interpreter. `qemu_plugin_entry_code()` также не принимается за entry главного ELF без проверки. `/proc/<host-qemu-pid>/maps` не используется как карта guest VA.
- Проверять принадлежность каждому конкретному PF_X-диапазону, а не всему интервалу между min/max: между сегментами возможны дыры. Неоднозначность/несовпадение хеша/байтов → `MappingError`, покрытие не засчитывается.
- Если QEMU повторяет guest layout и ASLR не даёт разных bias, тест нормализации дополнительно подаёт одну эталонную трассу с двумя синтетическими bias; результаты не выдаются за наблюдённую рандомизацию QEMU. В отчёт попадают фактически наблюдённые bias.

PIE-классификация для интерфейса: ET_EXEC → fixed-layout; ET_DYN с PT_INTERP и валидным entry в PF_X → кандидат динамического PIE, с отдельным признаком `DF_1_PIE`. Одного отсутствия DF_1_PIE или ненулевого первого PT_LOAD недостаточно для отказа. Неоднозначный ET_DYN без PT_INTERP (включая static PIE/библиотеку) — понятный `UnsupportedProfile` в MVP. Нельзя подменять фактическую нормализацию булевым `is_pie`.

### CFG, stripped и границы знания

Начать обход с ELF entry и проверенных адресов функций из символов или подсказки `main`, если они доступны. Следовать прямым переходам и вызовам, разбивать блоки по лидерам, сохранять обе ветви условного перехода. После call отмечать возможное продолжение; после return, безусловного перехода и терминатора обычного продолжения нет. Граф не учитывает контекст вызовов и не доказывает, что функция вернётся.

Для функций, недостижимых статически из entry (в том числе `main`, вызываемого libc через указатель), добавить ограниченный линейный поиск кандидатов в ещё не разобранных PF_X-байтах с меткой `Speculative`. Не считать их доказанным кодом. Секции, если есть, помогают сузить диапазоны, но PT_LOAD остаются основой. Неподтверждённые байты, невалидные инструкции и конфликтующие границы сохраняются как `UnknownRegion`; не «исправлять» поток простым пропуском байта без отметки.

Непрямой jump/call создаёт `Unresolved` с адресом инструкции и причиной. Полное восстановление таблиц переходов и функций не входит в MVP.

До мутаций выполнить начальные входы, проверить по трассе границы `Speculative`-блоков и обойти прямые цели подтверждённых участков. Это позволяет найти `main`, вызываемый через libc. Затем зафиксировать CFG: набор BlockId и знаменатель покрытия больше не меняются. Сохранённые адреса начальных запусков сопоставить с окончательной CfgRevision без повторного исполнения; записать исходную версию модели. Битовые наборы разных версий напрямую не объединяются. Новые неизвестные адреса во время фаззинга сохраняются как `UnmappedStatic` до следующего анализа.

В парном эксперименте обе кампании независимо выполняют одинаковые начальные входы с учётом этих запусков в бюджете. Перед мутациями проверяется равенство CfgRevision; при несовпадении пара исключается из сравнения процентов, причина сохраняется для диагностики.

| Состояние | Основание | Как показывать |
| --- | --- | --- |
| `Covered` | Наблюдён точный вход в валидированный блок с корректным mapping | Факт для перечисленных входов/запусков |
| `NotObserved` | Валидированный блок входит в область инструментации, в валидных запусках вход не наблюдался | «Не наблюдался при данном бюджете», не «невыполним» |
| `Unknown` | Предполагаемый блок, конфликт декодирования, ошибка сопоставления, неполный сбор или неизвестный переход | Причина неизвестности; отдельно от числителя/знаменателя покрытия |
| `OutOfScope` | Библиотека, JIT, неподдерживаемый процесс/поток | Не анализируется, явно указать |

Из частичного снимка можно засчитать только сохранённые посещения. Доля покрытия — число посещённых блоков относительно фиксированного набора проверенных блоков главного ELF. Отдельно вывести предполагаемые блоки, неизвестные байты, неразрешённые переходы, несопоставленные адреса и частичные запуски. Этот процент не охватывает весь бинарник. Посещение двух блоков не доказывает исполнение ребра между ними: **динамическая метрика MVP — входы в блоки; рёбра нужны для статической эвристики**.

### Запуски, таймауты и завершение

`runner` запускает аргументы без shell в отдельной группе процессов, с закрытыми лишними FD, отдельной рабочей директорией и входным файлом либо stdin до EOF. Фиксируются argv как массив, env по явному списку, cwd, stdin/file mode. Применяются timeout, лимиты памяти/CPU/размера вывода/файлов; значения находятся в manifest. По умолчанию stdout/stderr сохраняются до 1 MiB каждый с флагом truncation, остальное дренируется. Полноценная песочница для вредоносного ПО в MVP не разрабатывается; запуск экспериментов — в изолированной учебной VM, ограничения ресурсов не выдаются за sandbox.

Клиент и runner обмениваются версионированным header с RunId, BinaryId, CfgRevision, bias, готовностью mapping, execution bits, признаком ограничения профиля и complete-marker. Shared mmap принадлежит runner и читается после reaping; это предотвращает потерю всего покрытия при SIGKILL и не зависит только от atexit. Биты имеют прямой индекс блока без хеш-коллизий. ABI, порядок публикации header/битов и чтение частичного снимка фиксируются до реализации; незавершённый header → invalid coverage.

Исходы запуска: `Exited(code)`, `Signaled(signal)`, `TimedOut`, `Cancelled`, `UnsupportedRuntime(reason)`, `BackendError(reason)`, `SpawnError`. Код 139 сам по себе не доказывает SIGSEGV. В VF-03 проверить представление падений цели в QEMU; сохранять wait status, состояние клиента, stderr и результат повтора без QEMU. Если источник сбоя определить нельзя, записать `BackendError` с деталями.

Callback системных вызовов отслеживает `fork/vfork/clone/clone3/execve/execveat`; начальная загрузка цели не считается повторным exec. При попытке записать `UnsupportedRuntime` и остановить группу процессов. В VF-03 проверить гонку создания ребёнка и завершения группы. Демонизация с выходом из группы вне профиля; испытания выполняются в VM с внешним ограничением процессов. Если обнаружить создание потока/ребёнка до потери контроля не удаётся, QEMU не проходит VF-03.

По таймауту отправить TERM, через 100 ms при необходимости KILL, затем обязательно вызвать `wait`. При Ctrl-C остановить очередь, завершить группу, записать `cancelled` и частичный отчёт. Остальные причины завершения кампании: `max-execs`, лимит общего времени или невосстановимая ошибка исполнителя. Сохранить причину и число запусков. Таймаут одного входа не блокирует следующие.

### Корпус, цели и направленное достижение

Корпус адресуется SHA-256 входа. Начальные seeds сортируются по хешу; один worker и детерминированный RNG с записанным seed. Базовые операции: bit/byte flip, вставка/удаление/замена байта, малые арифметические изменения, splice с ограничением 4096 байт. Новый валидированный блок добавляет вход в активную очередь; crash/timeout сохраняются отдельно даже без нового покрытия. Replay не обязан воспроизводить порядок OS scheduling, но обязан проверять наблюдённое поведение сохранённого входа.

Первый алгоритм выбора цели прост: фронтир — `NotObserved`-блок с прямым предшественником `Covered`; затем ближайшие по кратчайшему статическому пути. Только валидированные блоки и разрешённые рёбра участвуют в расстояниях; переход через Unresolved означает неизвестное расстояние. Порядок по кортежу: меньше расстояние, меньше число прежних неудач, стабильный BlockId. Дополнительный флаг «редкий путь/константное сравнение» — объяснимая эвристика, не оценка вредоносности. Каждая попытка содержит seed, цель, score/reasons, бюджет и причину остановки.

Направленный метод MVP: для ближайшего условного перехода на разрешённом пути извлечь непосредственную константу `cmp` ширины 1/2/4/8 байт, связанного с `je/jne` без промежуточной записи флагов. Структурированные операнды должны сохранять ширину. Подставлять константу (и соседние значения только для заранее поддержанных сравнений) в каждую допустимую позицию входа, в little-endian; для 1-byte случая разрешить полный перебор 256 значений на ограниченном окне. Не выводить из `[reg+disp]` «смещение в файле» без доказательства: позиции входа перебираются и проверяются чёрным ящиком. Ограничить число кандидатов, длину и число попыток одной цели; неподдерживаемая форма → `UnsupportedCondition`, а не «условие решено».

Сохранять кандидата, если достигнут целевой или новый блок либо уменьшилась минимальная статическая дистанция от блоков **данного запуска** до цели. Сохранённые улучшения использовать для следующего байтового сравнения. Метод не решает контрольные суммы, криптографические условия и произвольный `memcmp`. Он меняет только вход цели.

### Уровни доказательности отчёта

| Уровень | Пример | Разрешённый вывод |
| --- | --- | --- |
| Наблюдаемый факт | Вход A не посетил блок B; на C процесс получил сигнал; D напечатал строку | Только наблюдение с RunId, адресом и входом |
| Эвристический признак | Условный фронтир с константой, ранее не наблюдавшаяся ветвь | Основание приоритета проверки |
| Гипотеза | Ветка может включать альтернативный режим работы | Нужны новый вход и проверка ожидаемого поведения |
| Подтверждённое поведение | Сохранённый вход повторно достигает блока и печатает маркер/вызывает падение | Воспроизводимое поведение в указанной среде |

Автоматические виды Finding: достигнут выбранный блок, наблюдён сигнал цели, превышен timeout. stdout/stderr сохраняются; маркер `TRIGGER` проверяет внешний тест. Повторное достижение блока подтверждает его достижимость; назначение блока по этому факту не определяется.

**Непокрытый участок сам по себе не доказывает недекларированную возможность.** Даже подтверждённый скрытый триггер без спецификации позволяет утверждать наличие поведения, но не его недекларированность. Для учебной фикстуры внешняя спецификация может задавать ожидаемый режим; это отдельный oracle эксперимента, не встроенный классификатор vulnFuzz. Поле `undeclared_verdict` в MVP отсутствует; `expected_behavior_reference` и комментарий исследователя необязательны.

## 4. Минимальные контракты до параллельной реализации

Предлагаемые структуры и примеры JSON согласуются в [VF-01](docs/BACKLOG.md#vf-01). `runner` вызывает одну реализацию исполнения и покрытия.

| Структура | Минимальные поля и инвариант |
| --- | --- |
| `BinaryId` | SHA-256 полных байтов; размер, исходный путь и ELF build-id — метаданные, не замена хеша |
| `CodeImage` / `ExecutableRange` | BinaryId, e_type, entry: ElfVa, вид размещения, PT_INTERP, PF_X-сегменты с адресами/смещениями/memsz и байтами; арифметика с проверками |
| `Instruction` | ElfVa, байты/размер, вид потока, непрямой переход/терминатор, операнды с width/index/scale, прямая цель или причина её отсутствия |
| `Block` / `Edge` | BlockId=(BinaryId,start VA), диапазон и начала инструкций, достоверность/источник; EdgeId=(from,to-or-unresolved,kind,site); виды: taken/fallthrough/jump/call/continuation/return/unresolved |
| `StaticModel` | BinaryId, CfgRevision=хеш канонической записи модели, блоки/рёбра/UnknownRegion, версия и параметры анализа; фиксируется до мутаций |
| `InputRef` / `CorpusEntry` | SHA-256 содержимого, путь, длина, родитель/мутация, первый RunId, наблюдённые BlockId; хеш проверяется при чтении |
| `RunSpec` | BinaryId, InputRef, argv, режим ввода, env, cwd, таймаут/лимиты, версия исполнителя, CfgRevision; запуск без shell |
| `RunResult` | RunId, хеш входа, исход, длительность, свидетельство exit/сигнала, ссылки на stdout/stderr и признак усечения, CoverageSnapshot, ограничения/ошибки |
| `CoverageSnapshot` | RunId, BinaryId, CfgRevision, bias, `set<BlockId>`, несопоставленные PC и признак переполнения, quality=`Complete/Partial/Invalid`, ошибки сопоставления; разные ELF/CFG не объединяются |
| `Target` | ID, BlockId, ребро фронтира/адрес условия, исходный InputRef, расстояние и причины приоритета, бюджет и прежние неудачи |
| `AttemptResult` | TargetId, RunId кандидатов, достижение по покрытию, прогресс, причина остановки=`Reached/Exhausted/Unsupported/Cancelled/Error` |
| `Finding` | ID, уровень доказательности, описание, ссылки на блок/сигнал/вывод, вход, исходный и повторные RunId, результаты с QEMU и без него, ссылка на спецификацию при наличии |
| `CampaignManifest` | Схема/версия, BinaryId и копия ELF, ссылка на StaticModel, SHA исполнителя/клиента/инструмента, toolchain, конфигурация, RNG, счётчики, статус/причина завершения |

Функциональные границы: `load -> CodeImage`; `analyze -> StaticModel`; `run_one(spec,input) -> RunResult`; `map(raw,model) -> CoverageSnapshot`; `update_corpus(run) -> novelty`; `select_target(model,coverage,history) -> Option<Target>`; `propose(target,seed,limit) -> candidates`; `write_report(events,model) -> artifacts`. Направленный модуль не запускает собственный процесс: каждый кандидат идёт через общий runner и счётчик кампании.

До параллельной разработки согласовать: координату VA и bias; идентификаторы ELF/CFG/входа; достоверность блоков и качество покрытия; исходы запуска; политику процессов; схему mmap с порядком байтов, размерами и атомарной записью; JSON v1; общий бюджет; file/stdin и структуру результатов. Изменения проверяют интегратор и автор затронутого модуля.

| I5: готовый MVP | [VF-19](docs/BACKLOG.md#vf-19), [VF-20](docs/BACKLOG.md#vf-20) | Парное сравнение baseline/guided, сырые данные и отчёт; чистая установка и демонстрация по README |

Перед I1 сходятся ветви `(VF-02 + VF-05 → VF-06 → VF-07)` и `(VF-03 + VF-04 → VF-08/VF-09)`, затем выполняются `VF-10 → VF-11`. Предварительный критический путь: **контракты → сбор адресов и bias → запуск/сопоставление → I1 → обычный фаззинг → выбор целей → направленные попытки → replay/проверки ограничений → эксперимент/приёмка**. Длительность ветви ELF/CFG и результат VF-03 могут изменить этот порядок. I1 требует обеих ветвей.

Если QEMU не проходит VF-03, записать причину и выбрать один резервный вариант. Разработка фаззинга на синтетических снимках может продолжаться, но I1 требует запуска с реальным сбором покрытия. Несколько исполнителей одновременно в MVP не разрабатываются.

## 6. Работа команды из 2–4 человек

Состав — рабочее допущение. Один из участников отвечает за интеграцию и `model.rs`.

| Направление | 4 участника | 3 участника | 2 участника |
| --- | --- | --- | --- |
| A: ELF/CFG, адреса | Разработчик A | A | A |
| B: QEMU/runner/coverage | Разработчик B | B | B |
| C: corpus/fuzz/analysis/directed | Разработчик C | A после I1 + B для интеграции | A после I1 |
| D: CLI/store/report/tests/эксперимент, интеграция | Разработчик D | C | B после I1, ревью A |

После общего ревью VF-01 задачи VF-02/03/04 могут идти параллельно в отдельных файлах. Изменения API согласовать до соединения модулей. Первый сквозной запуск I1 предшествует направленному поиску и эксперименту. Затем можно параллельно вести корпус/фаззер, анализ фронтира, проверки жизненного цикла и отчёт, используя согласованные снимки.

Возможные конфликты: `model.rs`, `Cargo.toml`, `Cargo.lock`, `lib.rs`, `main.rs`, схемы JSON и общий тестовый код. За общие типы и `lib.rs` отвечает интегратор; добавление зависимостей проходит его ревью. Переименования loader/disasm и перегенерацию экспериментальных отчётов выносить в отдельные PR.

Первая очередь для раздачи:

1. **Вместе / интегратор:** VF-01; принять адресную модель, значения unknown/covered и схемы на конкретном примере.
2. **A:** VF-02 — маленькие фикстуры и независимые адресные оракулы; затем VF-05 — ELF/PT_LOAD.
3. **B:** VF-03 — короткий эксперимент QEMU; затем VF-08 — жизненный цикл процесса.
4. **D при наличии:** VF-04 — сборка и проверки CI; затем каркас VF-11 на примерах схем.
5. **C при наличии:** после согласования VF-01 взять VF-12 — корпус с адресацией по хешам; фаззер VF-13 подключать после I1.

При двух участниках первые три пункта выполняются сразу, остальные распределяются после I0/I1. Каждый этап закрывается демонстрацией из таблицы и общедоступным для команды результатом с SHA инструмента и бинарника.

Ветки `vf-XX-short-name` создавать от свежего `main`; в PR включать один связный результат, ID задачи, ограничения и команду проверки с результатом. Нужен один ревьюер; изменения адресов, протокола или runner дополнительно проверяет автор соседнего модуля. Перед слиянием обновить базу и пройти обязательные проверки. Бинарники и результаты запусков не добавлять случайно. При изменении схемы описать миграцию либо отказывать в чтении несовместимой версии.

Задача готова, когда выполнены критерии приёмки, сохранён результат проверки, проверен ошибочный вход и интеграция с соседним модулем. При изменении интерфейса обновить контракт и инструкцию. Сборка без содержательных тестов не подтверждает функциональность.

## 7. Проверка метода и воспроизводимость

Разработчики и независимые тесты могут использовать исходники фикстур. CLI vulnFuzz получает **только бинарник и входы**; перекомпиляция или изменение кода цели не требуется. Исходники не используются для подсказок фаззеру.

| Фикстура | Нужное поведение и независимая проверка |
| --- | --- |
| `branches` | Ассемблерный участок с известными лидерами: последовательный код, прямой и условный переход, call/return; два входа дают заданные множества блоков. Проверяется этот участок, а не весь CRT |
| `trigger` | C-обвязка и маленький `.S`-участок с двумя последовательными `cmp byte, imm; je/jne`; особый двухбайтовый вход печатает `TRIGGER` и достигает отдельного блока; нейтральный двухбайтовый seed триггер не содержит |
| `benign_uncovered` | Редкая, обычная ветвь/неиспользуемая функция, без особого опасного поведения; исходное непокрытие не порождает вердикт о недекларированности |
| `crash_hang` | На разных входах нормальный выход, SIGSEGV через явную инструкцию и цикл; проверить классификацию и завершение процесса |
| `indirect` | Непрямой jump/call; в статике unresolved, при неизвестном динамическом PC — диагностика, без выдуманного ребра |
| `lifecycle` | Попытка fork/exec/thread, печать сверх лимита, Ctrl-C; статус UnsupportedRuntime/Cancelled, процесс не остаётся жить |
| `elf_bounds` | Не-ELF, усечённый ELF, другой class/arch/endian/type, overflow offsets/VA, NOBITS+exec, некорректные сегменты/entry, PF_X с дырой |
| Варианты сборки | `-O0 -fno-pie -no-pie`, `-O0 -fPIE -pie`, stripped-копии без debug info; отдельный валидный sectionless ELF с теми же PT_LOAD и исполняемым кодом |

Генератор записывает версии компилятора/линкера/strip, флаги и SHA-256. Оракул адресов рассчитывается из меток `.S` или карты линкера до strip и хранится отдельно по SHA; vulnFuzz его не читает. У файлов с символами и без них разные BinaryId, поэтому сравниваются адреса кода и поведение. Бинарники фикстур собирать в `target/fixtures`.

### Сравнение baseline и guided

Обе конфигурации используют одинаковый зафиксированный CFG, исполнитель, начальный корпус, базовые мутации, лимиты и машину. В guided дополнительно включены выбор цели и попытки из констант. Начальный корпус не содержит триггер; параметры фиксируются до измерений. Фикстура `trigger` проверяет работоспособность метода на заданном классе сравнений.

- Минимум **10 пар повторов** с RNG seeds 0–9 на `branches`, `trigger`, `benign_uncovered`, `crash_hang` в основной сборке. Для PIE/stripped — дополнительные сквозные проверки с отдельными результатами; проценты разных сборок не смешивать.
- Основной бюджет — 10 000 **всех** запусков на кампанию, timeout 200 ms, вход ≤4096 B. Подтверждения и направленные пробы учитываются; число запусков с мутациями показывается отдельно. Дополнительный режим — одинаковые 300 s с учётом статического анализа и генерации кандидатов. В VF-19 значения можно уточнить до эксперимента по измерениям I0, записав причину.
- Пары запускать последовательно, чередуя baseline/guided. Фиксировать CPU/ядро, RAM, ОС, загрузку машины, версии/SHA инструмента, QEMU и компилятора, env, argv, seeds и конфигурации.
- Метрики: число покрытых проверенных блоков, кривая покрытия по запускам и времени, время/число запусков до триггера, число подтверждений, exec/s, ошибки сопоставления/исполнителя, частичные снимки, таймауты и неизвестные области. Неразрешённые рёбра и предполагаемые блоки показываются отдельно. Для группировки падений использовать сигнал и адрес при наличии; такая группа не доказывает общую причину сбоя.
- Показывать результаты каждого повтора, медиану/IQR и число достижений из 10. Недостигнутый trigger — правое цензурирование на бюджете, не «успех за 10 000 запусков». Публиковать парные разности и сырые JSON/CSV; отсутствие улучшения является допустимым результатом.
- Ограничения: маленькие фикстуры, заданный класс сравнений, неполный CFG и особенности QEMU. Эти данные не доказывают эффективность на произвольном ПО или недекларированность поведения. Для статистических выводов десяти повторов может оказаться недостаточно.

## 8. Риски и открытые вопросы

| Риск | Ранний контроль | Действие при подтверждении |
| --- | --- | --- |
| API QEMU, адреса или контроль процессов не подходят | VF-03 | Записать причину, выбрать один резервный исполнитель и обновить задачи |
| CFG не охватывает `main`/непрямые вызовы без символов | Вызов `main` через libc и stripped-фикстура в I1 | Проверить границы по начальным запускам до фиксации CFG, остальное оставить неизвестным |
| Потеря покрытия при таймауте/падении | mmap, частичный снимок и тест KILL | Использовать только сохранённые положительные факты |
| Направленный поиск не даёт прироста | VF-15 и парные повторы VF-19 | Сохранить отрицательный результат и условия эксперимента |
| Поведение нестабильно или различается с QEMU и без него | VF-17 | Показать несовпадение и ограничить уровень подтверждения |
| Конфликты общей модели/бюджета | VF-01 и интеграции I0–I3 | Один владелец контрактов, небольшие изменения схемы с ревью |
| Слишком широкий профиль ELF | Матрица VF-02/05/18 | Явный UnsupportedProfile вместо универсальных обещаний |

Предлагаемые решения: один исполнитель на QEMU после проверки VF-03, покрытие входов в блоки без коллизий, ELF VA и PT_LOAD, частичный CFG, один worker, направленные мутации из констант, JSON/Markdown и повтор без QEMU.

Владельцу нужно уточнить: разрешена ли сборка QEMU и C-клиента в учебной среде; нужен ли для защиты конкретный бинарник со спецификацией; есть ли ограничения ресурсов для эксперимента. План пока исходит из Linux VM с QEMU, предложенных фикстур и бюджета раздела 7. Технические контракты согласует команда в VF-01/03.
